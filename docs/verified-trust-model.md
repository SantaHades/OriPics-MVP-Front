## 1. 두 티어가 각각 보증하는 것

**공통 (standard·verified 모두)** — "인증 시점 이후" 무결성:
- 인증 시점에 픽셀 해시(inner+border)를 서버가 **서버 전용 salt**(`ORIPICS_SALT_V2_*`, env 전용)로 서명(`final_hash`). 판독 시 서버가 재계산 검증.
- 한 픽셀만 수정돼도 판독 실패. 인증 시각은 서버 기록(timestamp)이 증명.
- 스탬프 알고리즘(`@oripics/stamp`)은 웹 JS로 공개되어 있어도 안전 — 위조 방지 근거는 알고리즘 비밀이 아니라 서버 salt (Kerckhoffs 설계). 알고리즘 지식으로 가능한 건 스탬프 읽기·제거뿐이며, 제거하면 "증명 없는 사진"이 될 뿐.

**standard 추가 보증: 없음** — 이미지 출처는 자기신고. 계정만 있으면 API 직접 호출로도 아무 이미지(편집본 포함)를 인증 가능. "이 시점부터 원본 봉인" 수준.

**verified 추가 보증** — "인증 요청의 출처":
- 앱 내 카메라 촬영(P)만 대상, Pro 이상.
- 서버 1회성 nonce(TTL 5분) → iOS App Attest / Android Play Integrity 하드웨어 attestation → 서버가 Apple 인증서 체인 / Google 서명 판정 검증 후에만 `tier=verified`.
- 즉 **"실제 기기의 정품 OriPics 앱이 그 시점에 인증 요청을 보냈다"**를 Apple/Google 하드웨어가 보증. 에뮬레이터·재패키징 앱·스크립트(API 직접 호출)는 통과 불가.

## 2. 공격 경로와 비용 (verified 기준)

| # | 공격 | 가능 여부 | 난이도/비용 | 비고 |
|---|---|---|---|---|
| 1 | 편집본을 갤러리에서 인증 | **차단** | — | verified는 P(카메라) 경로만 |
| 2 | API 직접 호출로 verified 요청 | **차단** | — | attest 토큰 위조 불가 (하드웨어 서명) |
| 3 | 재패키징 앱·에뮬레이터 | **차단** | — | App Attest 앱 ID 검증 / Play Integrity `PLAY_RECOGNIZED`·`MEETS_DEVICE_INTEGRITY` |
| 4 | attest 토큰 재사용·탈취 | **차단** | — | nonce 1회성·5분 TTL, 서버는 토큰 해시만 보관 |
| 5 | **루팅/탈옥 + 큐 파일 교체** | ~~가능~~ → **차단 상향 (2026-08-26 셔터 해시 봉인 구현)** | 상 — #6(런타임 후킹) 수준으로 통일됨 | 셔터(전처리)→[인증하기](후처리) 사이에 문서 디렉터리의 원본 JPEG를 편집본으로 교체하는 공격. §4-1 구현으로 파일 교체만으로는 불가 — 봉인 해시 불일치 시 인증 거부 |
| 6 | 루팅/탈옥 + 런타임 후킹 | **가능** | 상 — Frida류 계측, Android는 Integrity 우회 병행 필요 | 인증 순간 해시 입력 픽셀 바꿔치기. iOS App Attest는 탈옥 탐지가 아니라 상대적으로 열려 있음 |
| 7 | **아날로그 홀** (인쇄물·화면 재촬영) | **가능** | 하~중 — 탈옥 불요, 품질이 관건 | 어떤 소프트웨어 검증으로도 차단 불가. 센서 파이프라인 서명 하드웨어(라이카 M11-P류)조차 완전 차단 못 함 — **업계 공통 한계** |

**요약**: 캐주얼 위조(포토샵 후 인증, 스크립트 위조)는 확실히 차단 — 이것이 verified의 실질 가치. 남는 것은 표적 공격 수준(루팅 기기 준비 + 흔적 없는 편집)과 아날로그 홀.

## 3. 문구 가이드 (마케팅·분쟁 대응)

- ✅ 사용: "촬영 시점 기기 검증", "실기기 정품 앱에서 인증됨", "인증 이후 무편집 보증", "한 픽셀만 수정돼도 판독 실패"
- ❌ 금지: "위변조 **원천 차단/불가능**", "100% 진짜 사진 보증", "촬영된 장면이 실제임을 보증" — 표 2의 #5~#7이 반례가 되어 분쟁 시 법적 리스크

## 4. 강화 로드맵

### 4-1. 셔터 시점 해시 봉인 (A-48 — 공격 #5 대응) — ✅ **2026-08-26 구현 완료**

**아이디어(대표 제안)**: 셔터 순간 해시를 계산해두고 서버 서명은 [인증하기]에서 실행 → 촬영~인증 사이 파일 교체를 무력화.

**구현 (2026-08-26)**:
- `apps/mobile/src/lib/capture/seal.ts` — 셔터 직후 백그라운드 순차 작업(풀해상도 버퍼 메모리 경합 방지, 장당 ~1s)으로 픽셀 해시(inner+border) 계산 → SecureStore(Keychain/Keystore) 보관 HMAC 키(`oripics.seal_key_v1`, 32B 최초 생성)로 `HMAC(id|마크|해시|촬영시각|해상도)` 봉인 → 큐 항목 `seal` 필드에 저장.
- [인증하기] 시 진행 중 봉인 완료 대기(`awaitSeal`) → MAC 검증(실패=`seal_tampered` 거부) → publish 재계산 해시 대조(불일치=`seal_mismatch` 거부, 친화 문구 "촬영 후 원본 파일이 변경된 것으로 감지…").
- **인증마크 UX 변경**: 마크 포함 여부가 봉인 해시에 선행하므로 **촬영 화면 상단 pill로 이동**(GPS pill 패턴, 기본 ON) — 셔터 시점 확정. 목록탭 칩은 봉인 항목에서 잠금(탭 시 "촬영 시 확정됨" 안내). 갤러리(F) 항목은 기존 토글 유지(봉인 비대상 — verified 미적용 경로라 보안 가치 없음).
- **best-effort 정책**: 봉인 실패·부재(구버전 항목, 봉인 완료 전 앱 종료) 항목은 기존 흐름으로 인증. 사후 재봉인은 하지 않음(갭이 지난 봉인은 무가치 + 변조본 침묵 봉인 위험).

**원안 대비 수정점 (검토 결과)**:

1. **셔터 시점 "스탬핑"은 불가** — 스탬프 페이로드 = `meta + final_hash`이고 `final_hash`는 서버 salt 서명이라 서버 왕복 없이는 임베드할 수 없음. 셔터에서 가능한 것은 **해시 계산·보관까지** (임베드·업로드는 인증하기 시점 유지).
2. **해시를 큐 JSON에 평문 저장하면 무효** — 루트 공격자가 이미지 파일과 해시를 함께 교체 가능. 반드시 **Keychain/Keystore 키로 봉인**해야 함 (해시값을 SecureStore에 저장하거나, 큐 항목별 HMAC을 하드웨어 키로 생성해 동봉).
3. **효과**: 공격 #5(파일 편집 수준)가 #6(런타임 후킹 수준)으로 상향 — 가장 쉬운 경로가 제거되어 공격 비용이 상단으로 통일됨. 네트워크 불요(오프라인 촬영 유지).
4. **인증하기 시점 동작**: 재계산 해시 ≠ 봉인 해시 → 인증 거부 + "촬영 후 파일이 변경됨" 오류 표시 (변조 감지 UX 부수 효과).
5. **구현 제약**:
   - 인증마크(워터마크)가 해시에 선행하므로 **워터마크 옵션을 셔터 시점에 확정**하거나, 유/무 2종 해시를 모두 봉인해야 함 (현재는 목록탭에서 항목별 토글 — UX 변경 필요).
   - 해시 계산은 풀해상도 디코드+SHA256으로 장당 ~1초 수준 → 셔터 직후 **백그라운드 비동기**로 실행하면 연속 촬영(<0.3s) UX 유지 가능. 단 봉인 완료 전 수 초의 잔여 창은 존재(실질 무의미 수준).
   - attest nonce(TTL 5분)는 여전히 인증하기 시점 — 변경 없음.
6. **한계**: 서버는 해시 계산 시점을 구분할 수 없으므로 이는 클라이언트측 강화. 공격 #6·#7은 그대로 남음.

**판정**: "촬영 즉시 서버 서명"(네트워크 필수, 연속 촬영 개편 회귀)보다 훨씬 현실적인 절충. 오픈 후 여유 시점에 적용 권장.

### 4-2. 런타임 후킹(공격 #6) 대응 — A-49 (2026-08-26 검토)

- **기각: 셔터 시점 즉시 전체 파이프라인(서명·임베드까지) 실행** — 후킹은 시간 갭이 아니라 처리 길목(카메라 출력·해시 입력·파일 읽기)을 프로세스 내부에서 가로채므로 타이밍 압축은 무효. 비용만 큼: 촬영 시 네트워크 필수(오프라인 촬영 불가)·매 셔터 attest nonce·**셔터당 크레딧 차감**(버릴 사진에도 과금).
- **채택(A-49, 오픈 후)**: ①Android verified에 `MEETS_STRONG_INTEGRITY` 요구 상향 옵션(env 플래그 — 하드웨어 부팅 상태 증명, Magisk 은닉류 대부분 차단. 구형 기기 탈락 트레이드오프로 기기 분포 확인 후 활성) ②deviceIntegrity 수준(STRONG/DEVICE)을 links에 기록 — 분쟁 시 인증별 신뢰 근거.
- **보류**: RASP(freeRASP·Guardsquare류 — Frida/후킹 탐지). 비용 상향은 실질적이나 우회 가능한 군비경쟁 + 오탐 리스크 — PMF 이후 검토. iOS는 STRONG 등가물 없음(App Attest는 탈옥 탐지가 아님) — 탈옥탐지 휴리스틱은 기존 기각 유지.
- **궁극적 해법은 하드웨어**(센서/TEE 프레임 서명 — Qualcomm+Truepic류): 서드파티 앱에 미개방. 완전 장악된 기기의 자기 조작은 업계 공통 천장이며, 남는 공격자는 자기 계정·자기 사진을 조작하는 표적 공격자라 분쟁 시 스스로 위험 부담.
